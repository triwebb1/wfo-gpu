# Benchmarks

These are measured, reproducible throughput figures for the backtest stage on specific hardware. They are not comparisons: each row stands for the machine it ran on. Run the same command on your own hardware to see what to expect.

## Workload

`wfo-gpu-bench` (`bench/bench.cpp`) builds the same workload every time:

- **Bars.** A seeded synthetic series of 30-second bars over 30 US-futures sessions (82,800 bars), generated by `generate_synthetic_bars` with seed `424242`. The first 1,000 bars are signal warmup; the rest are evaluated.
- **Signals.** The full technical-indicator grid (every `IndicatorGrid` entry), computed and normalized to [-1, +1] once on the native path, so every device sees identical inputs. This time is reported separately and excluded from the throughput figures.
- **Strategies.** Two workloads of 20,000 distinct strategies each (redundant grid entries skipped), entry lag 1, E-mini-style costs:
  - `screen`: the first strategies in grid order, the way the screen enumerates them. At the default size these are all single-signal strategies, so neighbours share signals.
  - `sampled`: a fixed stride across the whole grid. Nearly all are four-signal strategies, with mixed aggregation modes, exit presets and trading-hours filters. This resembles a walk-forward reduced set, where strategies share little.

  The console report prints the signal-count mix of each workload.
- **Timing.** One warm-up pass per device and workload (kernel compilation, buffer allocation), then the median of five timed passes of `CLBacktest::evaluate`. GPU timings include host-to-device transfers and result download. Each batch is one kernel launch with work-items ordered by signal set and exit mode.

The two figures are:

| Metric | Meaning |
|---|---|
| Backtests/s | complete strategy backtests per second |
| Bar-evals/s | strategies x evaluated bars per second, i.e. how many (strategy, bar) steps the engine advances per second |

## Reproduce

```sh
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release
python tools/run_benchmarks.py --bench build/wfo-gpu-bench
```

The script prints the console report and ready-to-paste table rows. The native row honours `WFO_GPU_MAX_CPU_PCT` (default: all logical processors).

## Results

| Workload | Device | Hardware | OS, compiler | Strategies | Bars | Backtests/s | Bar-evals/s |
|---|---|---|---|---|---|---|---|
| screen | native (8 threads) | Intel Core i9-13900K host, VM with 16 virtual processors, 8 used | Windows 11, MSVC 19.44 | 20000 | 81800 | 3289 | 2.69e+08 |
| screen | OpenCL CPU | same VM, Intel CPU runtime, 8 TBB workers | Windows 11, MSVC 19.44 | 20000 | 81800 | 4615 | 3.77e+08 |
| sampled | native (8 threads) | same VM, 8 virtual processors used | Windows 11, MSVC 19.44 | 20000 | 81800 | 3202 | 2.62e+08 |
| sampled | OpenCL CPU | same VM, Intel CPU runtime, 8 TBB workers | Windows 11, MSVC 19.44 | 20000 | 81800 | 3119 | 2.55e+08 |

These rows were measured in a Hyper-V virtual machine with 16 virtual processors on an Intel Core i9-13900K host, with no GPU, limited to half its processors (`WFO_GPU_MAX_CPU_PCT=50`, `CL_CONFIG_CPU_TBB_NUM_WORKERS=8`). Repeated runs varied by up to about 10%. They show the CPU paths only; the GPU is where the kernel is meant to run, and rows for a discrete GPU are added the same way.

Rows are added by running the command above on the stated hardware; nothing here is estimated.
